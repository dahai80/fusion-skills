示例：思考模型空回复成因

部署：示例思考模型（GLM 系 chat template）· vLLM · LiteLLM 入口
本页数字为虚构示例，仅演示讲解版式
空回复有两类成因，机制完全不同：一类是模型确实输出了，但全在思考里（第一、二节）；另一类是客户端根本没等到结果（第四节）。

一、为什么"思考写满了"就是空

关键在于 GLM 怎么开始回答。它的 chat template 在提示词末尾固定拼上 <|assistant|><think>。也就是说，模型生成的第一个 token 就已经在思考块里面，它没有"跳过思考"这个选项。思考只能由模型自己输出 </think> 来结束。

vLLM 的 glm47 reasoning parser 按 </think> 切分输出：之前的内容归入 reasoning_content，之后的内容归入 content。

max_tokens 只有一个，思考和正文共用。如果思考还没结束预算就用完了，</think> 根本不会出现，于是全部输出都算作 reasoning，content 为空，finish_reason=length。

请求走 Anthropic 协议时，LiteLLM 把它转成一个 thinking 块、零个 text 块、stop_reason=max_tokens。Claude Code 收起思考块后，界面上看到的就是空白。

所以空回复不是模型出错，而是一道预算题：思考长度 > max_tokens。要解决，只有两条路：让思考变短，或者给正文留出预算。

二、思考为什么会那么长：参数在翻译链上丢了

问题叠了两层：

  1. GLM 模板只认两个档：reasoning_effort 为 low 或 high 才降档，其他任何值（不传、none、medium……）都按 Max 渲染。
  2. LiteLLM 的翻译没考虑 GLM：它把 Anthropic 的 thinking 按通用规则翻成 OpenAI 的 effort。disabled 翻成 none；adaptive 和 2048–4095 的 budget 翻成 medium。这三个值 GLM 都不认识，结果都是 Max。

最讽刺的是"关闭思考"反而得到最长的思考。Claude Code 有很多辅助调用，比如生成标题、做快速判断：它们关掉 thinking，max_tokens 只给几百到一千。按 Max 思考，几百 token 根本不够写完。

同一道题的 A/B 对比（不开 thinking，max_tokens 1024）：

输出 token耗时风险
无钩子（按 Max 思考）500–60012–16 s已经用掉一半多预算，题目稍难就撞上限
有钩子（按 Low 思考）150–2005–8 s余量充足

三、现在的两层防护和现网数据

第一层：thinking 钩子（预防）。在 LiteLLM 翻译之前，按客户端的原始意图改写成 GLM 认识的档位，再按 max_tokens 往下压，保证思考给正文留出空间：max_tokens 小于 16K 时 Max 降为 High，小于 4K 时 High 降为 Low。

第二层：代理截断补救（兜底）。如果思考还是撞了上限，代理会自动续写一次：把已有思考作为 <think>…</think> 接回去，并关掉 enable_thinking，让模型直接写正文。客户端收到的就是思考加正文。

上线以来只触发 2 次，2 次都成功，每次续写约 300 token、用时 15～20 s。触发得这么少，说明第一层已经挡住了绝大多数。

四、另一类：超时重试的雪崩

这一类与思考无关。负载高时，长 prompt 的 prefill 要排队：

  1. agent 大约 60 秒收不到首字就断开并重试；
  2. LiteLLM 不会把断开传给后端，所以旧请求接着算，新请求又排进来；
  3. 同一个 50K+ 的 prompt 被重复 prefill，队伍更长；
  4. 队伍更长，超时的请求更多，循环加剧。

被断开的那次请求，客户端拿到的就是空的。对应的修复：

  • "合并重复 prefill"代理：同一个 prompt 正在算的时候，重试直接挂到同一份结果上；
  • 后来上线的 KV 池和短请求优先，从源头缩短了排队：重启后不再从零 prefill，短请求也不会被长请求堵住。

一句话总结

GLM 被模板强制先思考，而思考和正文共用一个 max_tokens。参数在 LiteLLM 翻译时丢了，模型一律按最长档思考，预算在 </think> 之前就用完了，正文自然为空。负载高时，超时重试还会再叠加一层"根本没等到结果"的空。
